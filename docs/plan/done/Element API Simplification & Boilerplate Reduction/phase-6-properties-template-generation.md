## Objective

Provide a single CLI command that keeps a page's locator repository in sync with its enum declarations — from first creation through any future constant additions or removals. Developers fill locator values; the CLI handles everything else.

The `--sync` command orchestrates four steps in order:
1. **Template generation** — create the `.properties` file if absent; add missing keys if it exists
2. **Orphan detection** — warn for keys whose enum constant no longer exists
3. **Empty key validation** — fail with line numbers for any key that still has no value
4. **JSON generation** — write the conventional `.json` file from the validated properties

All four steps use the same key format and the same `ElementRole` source, eliminating any format mismatch between properties and JSON.

---

## Key Format

Every locator key is the fully-qualified dot-separated path:

```
PageClass.EnumClass.CONSTANT_NAME.ROLE
```

Where:
- `PageClass` — `pageClass.getSimpleName()` of the enclosing page interface
- `EnumClass` — `enumClass.getSimpleName()` of the inner enum
- `CONSTANT_NAME` — `((Enum<?>) constant).name()` (uppercase, underscore-separated)
- `ROLE` — `ElementRole.name()` of the locator role (uppercase)

The ROLE comes from iterating `element.getAllLocatorRoles().keySet()` — it is **always** `ElementRole.name()`, never derived from the method name. This is the same token `EnumLocatorScanner.writeInto()` already uses for the JSON sub-key.

**Examples:**

```properties
DemoLoginPage.Credentials.USERNAME_INPUT.INPUT=//input[@id='username']
DemoLoginPage.Credentials.PASSWORD_INPUT.INPUT=//input[@id='password']
DemoLoginPage.Button.LOGIN_BUTTON.TRIGGER=//button[@type='submit']
DemoLoginPage.Labels.SUCCESS_MESSAGE.TEXT=//div[@id='flash']

# Multi-role element
DemoLoginPage.NavBar.PARTNER.TRIGGER=//button[@data-partner]
DemoLoginPage.NavBar.PARTNER.LIST=//ul[@class='partner-options']
```

**Key derivation algorithm:**

```java
for each nested enum class in pageClass:
    enumSimple = enumClass.getSimpleName()
    for each enum constant:
        element = (Element) constant
        constantName = ((Enum<?>) constant).name()
        for each role in element.getAllLocatorRoles().keySet():
            key = pageSimple + "." + enumSimple + "." + constantName + "." + role.name()
```

No trimming, no casing transform — only `getSimpleName()`, `.name()`, and `ElementRole.name()`.

## Properties File Format

The generated file at the conventional path
`src/main/resources/<pkg/PageClass>/locators.properties`:

```properties
# PageClass — locators
# Generated by LocatorSyncCli. Fill XPath values only. Do not edit keys.
# Re-run --sync to add new constants. Use --prune to remove orphan keys.

# --- Credentials ---
DemoLoginPage.Credentials.USERNAME_INPUT.INPUT=
DemoLoginPage.Credentials.PASSWORD_INPUT.INPUT=

# --- Button ---
DemoLoginPage.Button.LOGIN_BUTTON.TRIGGER=

# --- Labels ---
DemoLoginPage.Labels.SUCCESS_MESSAGE.TEXT=
```

Rules:
- One `# --- EnumClass ---` section header per enum class, in declaration order
- Constants within each section in declaration order (not alphabetically)
- One blank line between sections
- When merging, new keys are appended to the correct section (or to the end if the section header does not yet exist)
- Existing keys and their values are never moved or modified

## Step 1 — Template Generation

### New file
1. Discover all nested enum classes in `pageClass` (using `getDeclaredClasses()`, filter to enums)
2. For each class, call `getEnumConstants()` and cast each to `Element`
3. Call `element.getAllLocatorRoles()` to get the `Map<ElementRole, String>` of roles
4. Derive the full key for each (role, constant) pair
5. Write the complete properties file with the format above

### Existing file (merge-with-preserve)
1. Load the existing file — use the line-tracking reader (see below) to preserve line numbers
2. Compute the expected key set from the current enum declarations
3. For each expected key not present in the file: append it to the correct section with empty value
4. Keys already present retain their values exactly — no change, even if the value is blank
5. Write the updated file back, preserving all existing content and ordering

---

## Step 2 — Orphan Detection

After loading the existing file, check each key against the live enum declarations.

**Parse algorithm:**
```
parts = key.split("\\.") with no limit
ROLE          = parts[parts.length - 1]        // last segment
CONSTANT_NAME = parts[parts.length - 2]        // second from last
EnumClass     = parts[parts.length - 3]        // third from last
PageClass     = parts[0..parts.length-4]       // remainder (joined)
```

For each key in the file, verify:
1. `ROLE` is a valid `ElementRole.name()` — if not, warn as **malformed key**
2. The (PageClass, EnumClass, CONSTANT_NAME) combination resolves to an existing enum constant in the loaded class

If any check fails:

```
[WARN] Orphan key in DemoLoginPage/locators.properties (line 12):
       DemoLoginPage.Credentials.OLD_FIELD.INPUT — constant 'OLD_FIELD' not found in Credentials
```

Orphan keys are never auto-deleted. The developer must either:
- Restore the removed constant, or
- Run with `--prune` to delete orphan keys explicitly

`--prune` deletes orphan keys from the properties file in place. It is never the default.

## Step 3 — Empty Key Validation

After template generation and orphan detection, validate that every **expected** key has a non-blank value.

**Line number tracking** — standard `Properties.load()` does not record line numbers. The implementation uses a `LineTrackingPropertiesReader`:

```java
// Internal implementation detail — not public API
class LineTrackingPropertiesReader {
    Map<String, Integer> lineNumbers = new LinkedHashMap<>();
    Properties properties = new Properties();

    void load(Path file) throws IOException {
        List<String> lines = Files.readAllLines(file, StandardCharsets.UTF_8);
        for (int i = 0; i < lines.size(); i++) {
            String line = lines.get(i).trim();
            if (line.isEmpty() || line.startsWith("#")) continue;
            int eq = line.indexOf('=');
            if (eq < 0) continue;
            String key   = line.substring(0, eq).trim();
            String value = line.substring(eq + 1).trim();
            lineNumbers.put(key, i + 1);  // 1-based
            properties.setProperty(key, value);
        }
    }
}
```

For any expected key with a blank value, the CLI prints:

```
[ERROR] Empty locator value in DemoLoginPage/locators.properties:
        Line  5: DemoLoginPage.Credentials.USERNAME_INPUT.INPUT=
        Line  6: DemoLoginPage.Credentials.PASSWORD_INPUT.INPUT=
        Line  8: DemoLoginPage.Button.LOGIN_BUTTON.TRIGGER=

Fill these values and re-run --sync. JSON generation skipped.
```

The CLI exits with code `1`. JSON generation does not run.

**Empty keys newly added** by this sync run are also reported as errors if not filled. This forces the developer to explicitly fill each value before the repository is considered valid.

## Step 4 — JSON Generation

If and only if Step 3 passes (all expected keys have values):

1. Call `JsonLocatorMigrator.writeResolvedJsonConventional(pageClass)` — this is the Phase 7 CLI's `--write-conventional` pipeline
2. The migrator reads from the properties file via `EnumLocatorScanner`, resolves each locator key against properties, and writes the JSON to `src/main/resources/<pkg/PageClass>/locators.json`

The JSON produced uses the **nested role object** format for all elements (both single-role and multi-role) — this requires the Phase 19 Part B change to `EnumLocatorScanner.writeInto()` (branch condition `roles.size() >= 1`):

```json
{
  "Credentials": {
    "USERNAME_INPUT": { "INPUT": "//input[@id='username']" },
    "PASSWORD_INPUT": { "INPUT": "//input[@id='password']" }
  },
  "Button": {
    "LOGIN_BUTTON": { "TRIGGER": "//button[@type='submit']" }
  },
  "Labels": {
    "SUCCESS_MESSAGE": { "TEXT": "//div[@id='flash']" }
  }
}
```

The JSON is the **primary runtime read file**. The properties file is the developer-editable source; the JSON is the generated artifact. Developers never edit the JSON directly.

## CLI Interface

Extension to `JsonMigratorCli`:

```
# One-shot sync: generate/update properties, validate, generate JSON
java JsonMigratorCli --sync  <fully.qualified.ClassName>

# Sync + delete orphan keys (destructive — prompts for confirmation)
java JsonMigratorCli --sync --prune  <fully.qualified.ClassName>

# Existing modes (unchanged)
java JsonMigratorCli --print               <fully.qualified.ClassName>
java JsonMigratorCli --write               <fully.qualified.ClassName>
java JsonMigratorCli --write               <fully.qualified.ClassName>  <outputFile>
java JsonMigratorCli --write-conventional  <fully.qualified.ClassName>
```

### Exit codes

| Code | Meaning |
|------|---------|
| `0` | All steps passed; JSON written |
| `1` | Empty key validation failed; JSON NOT written |
| `2` | Class not found or not a valid page interface |
| `3` | I/O error reading or writing files |

Orphan warnings always print to stderr but never change the exit code unless `--strict` is passed.

---

## Idempotency

Running `--sync` twice on a fully-populated file is a no-op:
- No new keys to add (all expected keys present)
- No empty values (all filled)
- JSON is regenerated but with the same content

The only observable effect of a second run is the JSON file's last-modified timestamp.

## Implementation Components

| Component | Responsibility |
|-----------|---------------|
| `LocatorTemplateGenerator` | Discover enum constants, derive keys, produce ordered key list |
| `LocatorTemplateWriter` | Write new file or merge into existing file |
| `OrphanKeyDetector` | Parse existing keys, cross-reference against live enums, report stale |
| `LineTrackingPropertiesReader` | Load `.properties` preserving per-key line numbers |
| `EmptyKeyValidator` | Check expected keys for blank values, collect line numbers, format errors |
| `JsonMigratorCli` | Wire `--sync` mode; sequence all four steps; handle exit codes |

These are internal classes in `core.resolvers.locator.json` or a new `core.resolvers.locator.sync` sub-package. No public API changes.

## Dependency on Phase 19 Part B

Phase 6 can be implemented in stages:

**Without Phase 19 Part B:** The CLI can generate, merge, detect orphans, and validate. The key format is already locked: `PageClass.EnumClass.CONSTANT.ROLE` with `ElementRole.name()`. The CLI derives keys from `getAllLocatorRoles()` — this is independent of what the locator methods return at runtime.

**Requires Phase 19 Part B:** `EnumLocatorScanner.writeInto()` must change its branch from `roles.size() > 1` to `>= 1` to emit the nested role object for single-role elements. This change is needed before Step 4 (JSON generation) produces the correct format.

In practice: implement all four steps together, with Phase 19 Part B as a prerequisite for the full sync.

## Exit Criteria

- `--sync` on a new page creates a correctly formatted properties file at the conventional path
- `--sync` on an existing file adds missing keys and preserves all existing values
- Orphan keys produce a warning with key name and line number; file is unchanged
- Empty keys produce an error with line number; exit 1; JSON is NOT written
- A fully-filled file produces a JSON at the conventional path with nested role objects
- Re-running on a filled file is a no-op (exit 0; same JSON content)
- All test matrix scenarios pass
- Full suite passes with no regressions

---

## What NOT to Do

- Do not auto-delete orphan keys — always require `--prune`
- Do not overwrite existing locator values — preserve is non-negotiable
- Do not write JSON if any key is blank — Step 4 is gated on Step 3 passing
- Do not derive the ROLE from method-name trimming — always use `ElementRole.name()`
- Do not use a format different from `PageClass.EnumClass.CONSTANT.ROLE` — the runtime resolver expects this exact format after Phase 19 Part B
