# I4.3 Pre-Implementation Audit -- Neutral Execution-Owner Contract

**Date:** 2026-07-29
**Branch:** `initiative/runtime-redesign`
**Scope:** Current state of the execution-owner seam before `Executor` is introduced.
Maps every design decision, verifies all preconditions, and sets the fitness-check
boundary that guards the central risk of the roadmap.

---

## Context

ADR-021 AD2 resolved: the neutral execution-owner concept is named `Executor`. It is a
kernel interface. `UIEngine` becomes the web domain's specialization of it. No kernel
type may reference `UIEngine` after I4. The `Executor` interface does not yet exist.

I4.3 is additive: `Executor` is introduced, `UIEngine extends Executor`, and the
registry is typed to the neutral contract internally. No caller is forced to migrate --
that is I4.4's job. The contract starts minimal; the fitness check is the only guard
against permanent domain-neutrality corruption.

---

## C1 -- `Executor` does not exist: the primary deliverable

`core.engine.Executor` (ADR-021 AD2, "or package TBD in I4") is not yet in the
codebase. The kernel membership table lists it as "introduced in I4; domain side
provides its implementation."

**Interface shape (minimum viable):**

Three methods are confirmed neutral by the LSP test -- a REST executor, database
executor, or CLI executor could implement each meaningfully without throwing:

| Method | Neutral? | Rationale |
|--------|----------|-----------|
| `void initialize(EngineConfig config)` | Yes | `EngineConfig` wraps JDK `Properties` + `Duration` only -- no Selenium, no UIElement (verified C4) |
| `void shutdown()` | Yes | Universal resource-release lifecycle |
| `String getEngineName()` | Yes | Identity, returns a plain `String` |

No other UIEngine method passes the LSP test for I4.3. Navigation methods
(`navigateTo`, `getCurrentUrl`, `refresh`) are web-domain. Resolution methods
(`resolve(UIElement, ElementRole)`) carry UIElement. Action methods (`click`, `type`,
etc.) are browser-specific. Waits and advanced methods are all web-domain.

**Package:** `core.engine` -- per ADR-021 AD2 ("core.engine.Executor or package TBD
in I4"). `core.engine` already sits in the kernel purity gate's exception list as a
managed boundary; placing `Executor` there is consistent.

**Fitness check (C5):** `Executor` must import nothing from `elements.*`, Selenium
(`org.openqa.selenium`), or `core.driver`. The fitness check is the only guard.

---

## C2 -- `UIEngine` carries UIElement and ElementRole: confirmed NOT on `Executor`

```java
// core/engine/UIEngine.java -- current imports
import elements.api.UIElement;
import elements.meta.ElementRole;

// These surface in:
LocatorDescriptor resolve(UIElement element, ElementRole role, Object... args);
```

`UIElement` and `ElementRole` are web-domain vocabulary. Neither may appear on
`Executor`. This is the most visible risk surface: `resolve(UIElement, ElementRole)`
is the single most-called UIEngine method and its signature is domain-specific by
definition.

A non-web executor (REST, DB) has no concept of a UIElement or locator role. Placing
`resolve()` on `Executor` would force every future executor to implement it by throwing
`UnsupportedOperationException` -- an LSP violation and a permanent neutrality breach.

**Conclusion:** `resolve()` and all other UIElement-bearing methods stay on `UIEngine`
only. `Executor` is unaware of them.

---

## C3 -- `EngineRegistrar.create()` return type: `UIEngine` → `Executor`

The plan's exit criterion: "registry operates on the neutral type." This means
`EngineRegistrar.create()` must return `Executor`, not `UIEngine`.

**Why this is safe in I4.3:**
- `UIEngine extends Executor` (new, introduced in I4.3).
- `SeleniumEngineRegistrar.create()` returns `SeleniumEngine` (a `UIEngine`, a `Executor`).
  Changing the declared return type to `Executor` is a source-compatible change for
  implementors since `SeleniumEngine` still satisfies the covariant return.
- Zero behavior change.

**Cascade into `UIEngineFactory.create()`:**

`UIEngineFactory.create()` currently assigns: `UIEngine engine = registrar.create(bootstrap);`

When `registrar.create()` returns `Executor`, this assignment needs a cast:

```java
// UIEngineFactory.create() -- bridge cast (I4.3, deleted in I4.4)
Executor executor = registrar.create(bootstrap);
UIEngine engine = (UIEngine) executor;   // safe: all I4.3 executors are UIEngine
```

`UIEngineFactory.create()` return type stays `UIEngine` for I4.3. The cast is a
documented bridge: it dies when `UIEngineFactory.create()` changes return type to
`Executor` in I4.4, after `VOIDBuilder`, `SessionContext`, `VOID`, `FlowExecutor`,
and `Action.perform()` are all retyped to the neutral signature.

**Risk:** a non-UIEngine executor registered after I4.3 but before I4.4 would throw
`ClassCastException` at session startup. This is an acceptable gap: I4.3 and I4.4
land on the same branch before merging; no intermediate state is released.

## C4 -- `EngineConfig` neutrality: confirmed safe

```java
// core/engine/EngineConfig.java
import java.time.Duration;
import java.util.Properties;
```

JDK types only. No Selenium, no `elements.*`, no `core.driver`. The three fields
(defaultTimeout, pollingInterval, baseUrl) and the raw Properties accessor are
domain-neutral -- any executor type can read what it needs and ignore the rest.

`Executor.initialize(EngineConfig)` is safe to place on the neutral contract.

---

## C5 -- Fitness check: new ArchUnit rule is the primary guard

The plan states: "fitness check forbids it importing anything UI." This must be encoded
in `KernelBoundaryRulesTest` before the interface lands, so the gate is active from the
first commit.

**Rule to add:**

```java
@Test(description = "Executor is a neutral kernel contract: no elements, Selenium, or driver (I4.3)")
public void executorContractIsNeutral() {
    ArchRule rule = noClasses()
            .that().haveFullyQualifiedName("core.engine.Executor")
            .should().dependOnClassesThat()
                .resideInAnyPackage("elements..", "org.openqa.selenium..", "core.driver..")
            .because(
                "Executor is the kernel's neutral execution-owner contract (ADR-021 AD2). " +
                "No UI vocabulary, Selenium, or driver infrastructure may appear on it. " +
                "A method a non-web executor could only implement by throwing does not " +
                "belong here. runtime-redesign I4.3.");
    rule.check(allClasses);
}
```

This check runs on every subsequent commit. Any accidental UIElement/Selenium import
causes a test failure before the branch can merge.

---

## C6 -- Kernel purity gate: no changes in I4.3

The `KERNEL_PURITY_TEMPORARY_EXCEPTIONS` set in `KernelBoundaryRulesTest` is
**unchanged in I4.3**. The exception for `core.engine.UIEngine` stays because
`Action.perform(UIEngine)`, `ActionHandler.execute(UIEngine, ...)`, and
`FlowExecutor(UIEngine)` are still UIEngine-typed -- that migration is I4.4.

In I4.4 the gate will be updated:

| Transition | When |
|------------|------|
| Remove `"core.engine.UIEngine"` exception | I4.4 (retyped to `Executor`) |
| Add `"core.engine.Executor"` exception | I4.4 (now the type in kernel signatures) |
| Remove `"core.engine.Executor"` exception | I9.4 (vocabulary rename; Executor moves or is re-packaged) |

I4.3 does not touch the gate's exception list.

## Change surface summary

| File | Change |
|------|--------|
| `core/engine/Executor.java` | New: `initialize`, `shutdown`, `getEngineName` |
| `core/engine/UIEngine.java` | `extends Executor` added |
| `core/engine/EngineRegistrar.java` | `create()` return type: `UIEngine` → `Executor` |
| `core/engine/UIEngineFactory.java` | Bridge cast `(UIEngine)` inside `create()` |
| `core/engine/selenium/SeleniumEngineRegistrar.java` | Declared return type of `create()`: `UIEngine` → `Executor` (implementation unchanged) |
| `core/architecture/KernelBoundaryRulesTest.java` | Add `executorContractIsNeutral()` |

`FlowExecutor`, `Action`, `ActionHandler`, `VOIDBuilder`, `SessionContext`, `VOID`:
**no changes in I4.3**. All changes to those types belong to I4.4.

## Risk register

| Risk | Severity | Mitigation |
|------|----------|------------|
| A UIEngine method is promoted to `Executor` during implementation | Critical | `executorContractIsNeutral()` ArchUnit rule fires immediately on any elements/Selenium import. The minimality rule (LSP test against a non-web executor) is the pre-implementation gate. |
| `EngineConfig` is later found to carry web-specific config | Low | EngineConfig is currently JDK-only (verified C4). Future additions to EngineConfig that introduce domain types would require a split -- but that is a future-phase decision. |
| Bridge cast `(UIEngine)` in `UIEngineFactory.create()` masks a non-UIEngine executor registration | Low | I4.3 and I4.4 land on the same branch; no intermediate state is released or testable independently. |
| `getEngineName()` on `Executor` uses the word "engine" -- terminology concern | Negligible | ADR-021 explicitly defers all vocabulary reclaim to I9.4. Name stays. |

---

## Verdict

**READY.** All preconditions are met. `EngineConfig` is neutral (C4). The UIElement
coupling on `UIEngine` is well-contained and confirmed absent from the `Executor`
shape (C2). Six files change; no caller is forced to migrate. The fitness check (C5)
is defined and encodes the central risk guard. Implementation order: add `Executor`,
extend `UIEngine`, update `EngineRegistrar` + `UIEngineFactory`, add the ArchUnit rule
(first commit, before the interface exists, so the gate is live from the start).
